# Internationalization

**Want to translate KoalaCast into your language?** Jump to
[Adding a language](#adding-a-language). It is one JSON file and one line of
registration — no build step, no tooling to install.

---

KoalaCast separates two things that are easy to confuse:

| Preference | Stored as | Controls |
| :--- | :--- | :--- |
| **Interface language** | `koalacast_ui_language` | The language KoalaCast's own UI is rendered in |
| **Content languages** | `koalacast_preferred_languages` | Which podcasts Discover and Search return |

They are independent on purpose: wanting a German interface and wanting only
German podcasts are different preferences, and plenty of listeners want one
without the other.

Neither is a *region*. See [Language vs. region](#language-vs-region).

---

## Adding a language

1. **Copy the English catalogue.**

   ```bash
   cp apps/web/src/lib/i18n/messages/en.json apps/web/src/lib/i18n/messages/fr.json
   ```

2. **Translate the values.** Leave the keys alone. Keep every `{placeholder}`
   exactly as it appears — they are filled in at runtime.

3. **Register it** in `apps/web/src/lib/i18n/registry.ts`:

   ```ts
   { code: 'fr', name: 'Français', flag: '🇫🇷', load: () => import('./messages/fr.json') }
   ```

   `name` is the endonym — a language is always listed in its own language.
   Add `rtl: true` for right-to-left scripts; the app sets `dir` accordingly.

4. **Check your work:**

   ```bash
   npm test && npm run check:i18n
   ```

   The test suite runs over every registered language, so yours is validated the
   moment you register it — no test file to write.

That is the whole process. The language now appears in Settings → Interface
Language.

### You do not have to finish

A partial translation is welcome. Any key you leave out falls back to English
for that string only — the app never breaks and never shows a blank. `npm run
check:i18n` reports missing keys as warnings, not errors, so a first pass can be
merged and improved later.

### What CI enforces

Both `npm test` and `npm run check:i18n` run on every pull request. They **fail**
on problems that would break the UI rather than merely leave it untranslated:

- a key that does not exist in `en.json` (usually a typo)
- a `{placeholder}` that is missing, misspelled, or invented
- a plural entry that is a plain string, or a plain string that became a plural
- a plural entry missing the `other` form
- an empty or whitespace-only value
- leftover `TODO` / `FIXME` / `PLACEHOLDER` text
- a value that is just the key echoed back
- leading or trailing whitespace
- a plural category your language never selects (e.g. `few` in German)
- a catalogue file that is not registered, or a registered locale with no file

The catalogue tests live in `src/lib/i18n/catalogues.test.ts` and are
data-driven: they iterate `LOCALES`, so a language added later is covered
automatically.

Add `--strict` to also fail on untranslated keys, for a language you consider
complete.

## Plurals

Plural-sensitive strings are objects keyed by
[CLDR plural category](https://cldr.unicode.org/index/cldr-spec/plural-rules):

```json
"showCount": {
	"one": "{count} Show",
	"other": "{count} Shows"
}
```

Selection uses the platform's own `Intl.PluralRules`, so a language needing more
categories than English just adds them — **no code change**:

```json
"showCount": {
	"one": "{count} podcast",
	"few": "{count} podcasty",
	"many": "{count} podcastów",
	"other": "{count} podcastu"
}
```

Only `other` is mandatory; it is the fallback when a category is absent. Call it
with a `count` param and the runtime picks the form:

```svelte
{t('discover.showCount', { count: podcasts.length })}
```

## Using it in a component

```svelte
<script lang="ts">
	import { t } from '$lib/i18n';
</script>

<h1>{t('discover.forYou')}</h1>
<p>{t('discover.noResults', { query })}</p>
```

`t()` reads reactive locale state, so components re-render on a language switch
without a reload.

**Module-scope values are evaluated once and will not update.** Use `$derived`:

```svelte
<!-- wrong: frozen at the initial language -->
const links = [{ href: '/library', label: t('nav.library') }];

<!-- right -->
const links = $derived([{ href: '/library', label: t('nav.library') }]);
```

For numbers, `n(value, options)` formats in the active locale.

### Legal content is not translated

**The privacy policy and any other legal text stay in English, deliberately.**

A mistranslated clause in a privacy policy is a legal problem, not a cosmetic
one — and a policy that says subtly different things in different languages is
worse than one that says it only in English. The English text is the version
that gets reviewed and signed off, so it is the only version published.

This means:

- `apps/web/src/routes/privacy/+page.svelte` and
  `apps/web/src/lib/data/privacy.ts` contain no `t()` calls. Keep it that way.
- Footer links that *name* a legal document ("Privacy Policy", "Legal Notice",
  "MIT License") also stay English, so a translated label never promises a
  translated page.

`find-untranslated.mjs` will report these strings. That is expected — they are
not oversights.

If a translated policy is ever wanted, it needs a lawyer's review per language
and a clause naming the authoritative version, not a JSON key.

### Strings that must not be translated

Some English strings are protocol values, not UI text. Genre names are the
clearest case: `GENRES[].name` is sent as `?category=Technology` and matched
against a podcast's own categories, so it stays English on the wire while
`genreLabel()` renders the translated label. The UI shows "Technik"; the request
still says `category=Technology`.

Brand names (KoalaCast, GitHub, Podcast Index, Value4Value) are intentionally
untranslated.

## Architecture

No i18n library. Catalogues are plain JSON, plural selection uses the platform's
CLDR data, and the reactive layer is a few lines of Svelte 5 runes. This keeps
the static SPA bundle small, avoids a build step, and — because JSON is what
translation platforms (Weblate, Crowdin, Lokalise) speak natively — lets
contributors submit a language without touching code.

```text
apps/web/src/lib/i18n/
├── registry.ts          Locale list + loaders. The only file a new language edits.
├── runtime.svelte.ts    t(), n(), plural selection, reactive locale state
├── index.ts             Public API — components import from here
└── messages/
    ├── en.json          Source of truth; defines the key set
    └── de.json
apps/web/scripts/
├── check-translations.mjs   CI parity + placeholder validation
└── find-untranslated.mjs    Audit for hardcoded strings
```

`registry.ts` is deliberately dependency-free: the preferences store resolves a
locale while initializing and the runtime reads that store, so keeping the pure
parts separate breaks the import cycle.

**Type safety.** `MessageKey` is derived from `en.json` via `resolveJsonModule`,
so `t()` has autocompletion and a typo is a compile error — without a codegen
step. Plural nodes are treated as leaves, so `t('discover.showCount.one')` is
rejected.

**Lazy loading.** Only English is bundled (it is the fallback). Every other
locale is a separate chunk fetched on demand, awaited in `+layout.ts` before
first paint so a non-English UI never flashes English.

**Fallback chain.** active locale → English → the key itself. A missing string
shows up as `search.foo`, which is obvious in review rather than invisible in
production.

### Auditing

```bash
node apps/web/scripts/find-untranslated.mjs --verbose
```

Heuristically reports hardcoded text in markup, `aria-label`/`title`/
`placeholder` attributes, and toast calls. Brand names legitimately appear here.

## Content languages (which podcasts you see)

### Language vs. region

These are **not** the same thing, and conflating them was a real bug:

- A **region** is an iTunes storefront (`us`, `de`). The German storefront is
  full of English-language shows.
- A **language** is what is actually spoken, from the feed's RSS `<language>` tag.

Filtering by region alone can never produce a German-only chart. The client
sends both: `region` selects which chart to pull, `languages` filters what comes
back.

```http
GET /api/v1/podcasts/discover?region=de&languages=de&limit=60
GET /api/v1/podcasts/search?q=news&region=de&languages=de&category=News
```

Because charts are region-scoped rather than language-scoped, Discover
over-fetches (see `languageFilterOverfetch`) so a page still fills after
non-matching entries are dropped.

### How a podcast's language is determined

In descending order of trust:

1. **The RSS `<language>` tag**, for any feed already stored locally. Authoritative.
2. **Podcast Index**, which reports a language per feed. Authoritative.
3. **Heuristic detection** (`services/api/internal/lang`) over the title and
   description, using stopword frequency and distinctive characters (`ß`, `ñ`).

A podcast whose language cannot be determined is **kept, not hidden**. Dropping
unknowns would silently hide every feed whose publisher merely omitted the
`<language>` tag.

### Known limitation: iTunes search

The iTunes chart endpoints return a description, so detection has enough text to
work with — coverage on a 60-item chart is effectively complete.

The iTunes **search** endpoint returns only a title and author, which is usually
too little to call a language. Most search results therefore come back as
unknown and — by the rule above — are kept. **The language filter is
consequently weak on search when iTunes is the provider.**

Configuring `PODCAST_INDEX_KEY` / `PODCAST_INDEX_SECRET` resolves this: Podcast
Index reports the real language for every result, and the filter becomes exact.

### Adding a content language

Content languages are separate from UI locales — you can filter podcasts by a
language the interface is not translated into. Add an entry to
`SUPPORTED_LANGUAGES` in `apps/web/src/lib/data/languages.ts` (with the iTunes
storefront to pull charts from) and to `Supported` in
`services/api/internal/lang/lang.go`. Adding stopwords for it in the same file
improves detection where no `<language>` tag exists.
